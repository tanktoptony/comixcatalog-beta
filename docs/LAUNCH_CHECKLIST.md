- [ ] **Open P0 defects: 0**
  - Owner:
  - Evidence: First real end-to-end QA pass on the auth surface (2026-09-13), driven live against a headless-Chromium session (Playwright, not just a code trace) plus direct DB verification via the service-role key. Found and fixed 3 live P0s, all confirmed resolved by re-running the same repro after the fix:
    1. `src/app/auth/callback/route.js` called `launchProfileFlags()` without importing it — every email-confirmation completion for a signup with a username in metadata (i.e. essentially every real signup, wherever Supabase email confirmation is on) threw `ReferenceError` server-side instead of finishing signup. Fixed: added the import.
    2. `src/lib/supabase/server.js`'s `supabaseServer()` called `cookies()` synchronously — Next 16 made it async, so every call threw `TypeError: cookieStore.get is not a function`. This crashed `/auth/callback` (compounding with #1 above — this crash fired *before* reaching the missing-import line) and `/api/account/delete` (reproduced live: real 500 "Could not read session"). Separately, even with `await` added the cookie it read (`sb-access-token`) was never real — the browser client persists sessions in localStorage, not cookies, so no server route using it could ever identify a caller. Fixed by switching to explicit bearer-token forwarding (client sends `Authorization: Bearer <access_token>` from `supabase.auth.getSession()`; the route validates it via `supabase.auth.getUser(token)`).
    3. `/api/account/delete` never deleted `comics`/`comic_covers` rows the user created (e.g. via CSV import or "+ Add manually"), so `auth.admin.deleteUser()` failed on a foreign-key violation the moment a user had added even one local comic — an unrecoverable "Database error deleting user," permanently blocking that account's deletion. Found via a live repro (CSV-imported a comic, then couldn't delete the test account) and confirmed via direct queries against `comics`/`comic_covers`/`profiles`/`auth.users`. Fixed: delete comic_covers → comics → user_collections → profile → auth.users in FK-safe order; re-verified the same account then deleted cleanly end to end.
    All 3 fixes are in this PR (`agent/qa-auth-pass`) along with a 4th fix classified P1 (see below). `npm run build` and `npx eslint` on all 5 changed files are clean (0 errors).

    - **Open — CSV import data quality:** importing a CSV with a populated `series_title`/`issue_number`/`publisher` (e.g. "The Amazing Spider-Man,1,Marvel") creates a local `comics` row with `series_title`/`publisher`/`release_year` all `null`, rendering as "Untitled #1 · Unknown Publisher · Unknown Year" in the library instead of matching the real catalog or preserving the imported values. Reproduced live twice. Root cause is in the CSV import/matching path, which this pass didn't otherwise touch or trace — needs a real look, not a guess.
    - **Fixed (agent/auth-polish, 2026-09-13):** signup password minimum standardized to 8 characters. `/signup` was accepting 6 while `/reset-password` and the account-settings change-password form both required 8; `src/app/signup/page.js`'s validation, error copy, and the input's `minLength` now match the other two. Verified via `npm run build` (clean) and a live dev-server check of the rendered signup HTML confirming `minLength="8"` on the field.
    - **Fixed (agent/auth-polish, 2026-09-13):** corrupted/fully-invalid local session no longer shows a raw error on `/library`. Root cause: a session with garbage access+refresh tokens (not normal expiry — the SDK's silent refresh already handles that) still passes `AuthContext`'s local session check because the stored `expires_at`/`user` look structurally valid, so `user` becomes truthy and `LibraryContext.refreshLibrary()`'s `user_collections` query fires with the bad token, which Supabase rejects with an opaque `"JWT cryptographic operation failed"`. Fixed in `src/context/LibraryContext.js`: a new `isAuthTokenError()` check on that query's error/catch path now detects this class of failure and calls `supabase.auth.signOut({ scope: "local" })`, which fires `SIGNED_OUT` → `AuthContext` sets `user` to null → the existing `/library` and `/account` redirect-to-`/login` guards take over, same as any other logged-out visit. Verified against the real Supabase project (not a mock): a Node script seeded a fake-storage session with garbage tokens through the actual installed `@supabase/supabase-js` client, reproduced the exact `"JWT cryptographic operation failed"` error on the same query LibraryContext runs, confirmed `isAuthTokenError()` matches it, and confirmed `signOut({scope:"local"})` clears the session and fires `SIGNED_OUT` even though the tokens are garbage (GoTrue treats the resulting 401 from its own server-side logout call as an expected/ignorable case and clears local storage anyway).
    - **Reviewed, left as-is:** Supabase's infra-level rate limiting on login/signup. `src/app/login/page.js` had no explicit rate-limit branch at all (fell through to raw `error.message`, which for GoTrue's real rate-limit errors is already human-readable, e.g. "For security purposes, you can only request this after N seconds") and `src/app/signup/page.js` only matched the literal substring "rate limit". Both now explicitly catch `rate limit` / `too many requests` / `for security purposes` / HTTP 429 and show a plain "Too many \[login/signup\] attempts. Please wait a few minutes and try again." — not force-triggered against the live rate limiter to avoid burning the project's real limit budget; verified by code trace against GoTrue's documented error shapes instead.
    - **Also shipped this pass (agent/auth-polish, not from the original audit list):** `/signup` and `OAuthButtons.js` (used by both `/login` and `/signup`, currently commented out on both pending the OAuth-UX fix mentioned elsewhere in this doc) now show a low-friction "by continuing you agree to our Terms of Service and Privacy Policy" notice linking to the existing `/terms` and `/privacy` pages — previously `/signup` had zero reference to either.
    - **Open — CSV import data quality:** importing a CSV with a populated `series_title`/`issue_number`/`publisher` (e.g. "The Amazing Spider-Man,1,Marvel") creates a local `comics` row with `series_title`/`publisher`/`release_year` all `null`, rendering as "Untitled #1 · Unknown Publisher · Unknown Year" in the library instead of matching the real catalog or preserving the imported values. Reproduced live twice. Root cause is in the CSV import/matching path, which this pass didn't otherwise touch or trace — needs a real look, not a guess.
    - **Open — cosmetic:** the onboarding modal can pop up over the signup form mid-submission and over the header immediately after a fresh login (it's mounted at the root layout and fires 800ms after `user` becomes truthy, regardless of which page that lands on). Working as designed, just poorly timed relative to the auth moment itself. Also, deleting an account races the account page's own logged-out-redirect effect against the explicit post-delete `window.location.href = "/"`, producing a brief `/login` flash and one benign console 403 before landing correctly on `/` — final state is always correct.

    - **Google OAuth session race — root-caused and fixed (agent/oauth-session-fix, 2026-09-13), OAuth still left OFF.** OAuth sign-in had been commented out on `/login` and `/signup` since 2026-06-16 over "a clunky flow." Root cause: `src/app/auth/callback/route.js` ran `exchangeCodeForSession(code)` on a throwaway server-side `supabaseServer()` client with nowhere to persist a session (no cookies — this app is localStorage-only, see `src/lib/supabase/server.js`), then redirected straight to `/u/<username>`. The exchange itself succeeded server-side, but `AuthContext` reads only from the browser's own persisted client, which never saw any of it — a user who'd "successfully" signed in landed on their profile page already logged out. Fixed: `/auth/callback` is now a client-rendered page (`route.js` → `page.js`) that runs the exchange on the browser's own singleton client (`getSupabaseClient()`, `persistSession: true`) instead, so the resulting session actually lands in localStorage this time. It handles both redirect shapes GoTrue can hand back (hash-fragment `#access_token=` via the SDK's own automatic detection, and query-string `?code=` via an explicit `exchangeCodeForSession(code)` call, since this client isn't configured with `flowType: "pkce"` so the SDK's automatic PKCE detection never self-triggers) rather than assuming one. The username-check/profile-upsert/`/complete-profile` redirect logic that used to run server-side now runs client-side after the session exists, reusing the same client-side `profiles` upsert pattern already used by `/signup` and `/complete-profile` (RLS-permitted under the anon key, no new API route needed). `/complete-profile` copy also now explains why the user landed there and pre-fills a suggested username from the OAuth-supplied name/email where derivable. **Verification:** no real Google account or browser-automation tool was available in this environment, so the actual Google-consent hop was NOT driven end-to-end — that specific gap is unverified. What WAS verified for real: a Node script drove the identical client-side session-exchange code path against the live production Supabase project (not mocked) using a genuine one-time token minted via `admin.generateLink`, simulating a browser via fake `window`/`localStorage` globals with the real installed `@supabase/supabase-js` — confirmed a real session gets written to (simulated) localStorage, that a second independent client instance sharing that storage recovers it (proving the exact persistence race is closed), and that the profile upsert (including the launch promo flags) succeeds under real RLS with the real user's JWT. The `?code=`-shaped branch was verified the same way with the SDK/persistence logic real but the GoTrue network response mocked (no admin API can mint a genuine PKCE `?code=` link — it requires a browser that already holds a matching code_verifier, which an out-of-band link never has). Test accounts were deleted after each run. Given the Google-specific hop is still unverified, **OAuth was left commented out** in `/login` and `/signup` rather than re-enabled — re-enable only after a real Google sign-in has been walked through once, live.
