# Service-role route audit — 2026-10

Scope: H5 Phase A only. Audited every `src/app/api/**/route.js` file that creates a service-role Supabase client or reaches one through a helper in `src/lib`. The plan said 79 files; the code currently has **87** such route files. Shared paths traced include `getServiceClient`, `adminClient`/`ownedCopy`, `marketplace`, `productionAssetsServer`, `orderRoute`, `messageEmail`, and order-event/refund helpers. “Checked” below means request identifiers are either public catalog selectors, derived from the verified caller, or ownership/role-bound before private data is returned or changed. Database RPC claims are based only on SQL present in this repository; otherwise they are marked **needs check**.

## Findings

No verified high-, medium-, or low-severity authorization findings were found. In particular, no route was verified to let user A obtain or change user B’s private data or money by substituting a path, query, body, username, or slug value.

Items marked **needs check** are not findings: their final authorization is inside a database RPC or external provider behavior that cannot be completely proved from the route alone.

## Deployed RPC grants (verified 2026-10-15)

The **needs check** rows above depend on database functions that take a user id argument (`p_buyer`, `p_author`, `p_user_id`, `p_admin`, and so on). The risk would be a browser calling one directly through `/rest/v1/rpc` with someone else's id. Claude queried prod (`pg_proc`, `has_function_privilege`) for every public function whose arguments name a user, buyer, seller, author, owner, actor, admin, follower or uid:

- 33 of 36 are `SECURITY DEFINER` with **no** `anon` or `authenticated` execute grant. Only the service role can call them, which means only through the audited routes, and those always pass the verified caller's id.
- `mkt_seller_rating(p_seller)` and `mkt_seller_ratings(p_sellers)` are executable by `anon`/`authenticated` on purpose: seller ratings are public.
- `order_ship_to(p_order)` is executable by `authenticated` and derives the caller from `auth.uid()`, so it doesn't trust an argument.

Result: no user-id RPC can be pointed at another account from the client. With that, the **needs check** rows resolve to ok at the grant level. Whether each RPC also re-checks party membership internally is defense in depth, not a reachable hole.

## Coverage notes

- Service client factories verified: `src/lib/supabase/service.js`; direct inline factories using `SUPABASE_SERVICE_ROLE_KEY`; `src/lib/listingPhotosServer.js`; and `src/lib/productionAssetsServer.js`.
- Indirect route use verified through `src/lib/marketplace.js` (including the in-process `library-hydrate` call), order helpers/events/refunds/emails, and message email delivery.
- Public-by-design routes were still checked for visibility predicates. A service-role client does not make a route private by itself; the response contract and filters determine whether the exposed data is intended public data.
- This was a code-only audit. Deployed database function bodies and production configuration were not queried; rows relying on those are explicitly marked **needs check**.
